Personal Finance Copilot

A deterministic finance engine with the language model kept strictly outside the calculation boundary. The model reads a transaction and proposes a category; every dollar figure downstream is computed in exact decimal by code that never calls it.

That boundary is only worth drawing if the model half is measured, so it is. Below is what it scored against a deterministic baseline, the two prompt changes that were measured against it — one rejected, one adopted — and what the model still gets wrong.

Public demo mode. Real financial ingestion is disabled on this deployment by design. The new workbench reads only synthetic in-memory rows; it never accesses tenant transactions or uses a model API key.

Every figure on this page is an aggregate. No transaction, amount, merchant, date, or per-row prediction is published here or reachable from here. The evaluations ran locally against real statements; only the counts travelled.

How the benchmark was built

Three decisions do most of the work here, and each of them makes the reported number smaller rather than larger.

The split is merchant-disjoint, not random

Rows are assigned by a salted hash of the normalised merchant, so every transaction from one merchant lands on the same side. A shuffled split would put four rows from one grocery chain in development and a fifth in evaluation, and the score would be measuring memorisation of a merchant string. Merchants appearing on both sides: —.

It is a frozen validation benchmark, not a test set

The v1 results informed the design of v2. Once results shape a decision, the rows that produced them can no longer serve as a held-out test set, and calling them one would claim more than they can support. They are frozen, and they are honest about what they are.

Four metrics, because each is misleading alone

Macro F1 weights every category equally, so a model that ignores rare categories cannot hide behind the common ones. Weighted F1 says what a typical row experiences. Coverage and accuracy-when-answered separate declining to guess from guessing wrong. They are reported together on purpose — see the prompt iterations below for what happens when one of them is read on its own.

Ambiguity is authored, never inferred

The two annotation passes disagreed on 31 of the 400 labelled rows. It would be easy to call those ambiguous and let either label count as correct, and it would raise every system's score. It is refused here, because disagreement usually means one pass was wrong. Those rows are still reported as a difficulty stratum, which measures whether the model struggles where the annotator did, and claims nothing about the rows having two right answers.

On reading macro F1

Macro F1 is not a misleading metric — it is the one that stops a model hiding a rare class it ignores, which is why it is a headline here. Deciding on macro F1 alone is what misleads, and this benchmark has produced a clean example of why: the average divides by the number of labels in play, so a system that simply stops predicting a label it was never right about raises its own score without answering anything better. Every macro move above is therefore published with its denominator and its summed F1, so the half that is real can be told from the half that is arithmetic.

Architecture

The constraint that shapes everything: the model is a proposal, never a calculation.

  • The domain layer is standard-library only. No framework, no ORM, no HTTP client can be imported into it. An import-linter contract fails the build if one is, so the rule is enforced rather than documented.
  • Money is Decimal end to end, and crosses the HTTP boundary as a string. A contract test scans every response for a JSON float and fails on any of them.
  • The model sits behind a port. The prompt is a versioned artifact (categorise/v1), the provider is swappable, and the labels, split, and scoring stay fixed across providers so a second vendor can be scored on the identical benchmark.
  • Imports are fingerprinted and versioned. Every transaction carries a reproducible fingerprint and an occurrence number; snapshot and incremental modes have defined, and different, duplicate semantics, and an account cannot silently switch between them.
  • Tests run against real PostgreSQL in CI, not SQLite. Partial unique indexes and JSONB behave differently enough that a passing SQLite suite would be evidence of nothing.
