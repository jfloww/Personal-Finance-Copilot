Personal Finance Copilot

A deterministic finance engine with the language model kept strictly outside the calculation boundary. The model reads a transaction and proposes a category; every dollar figure downstream is computed in exact decimal by code that never calls it.

That boundary is only worth drawing if the model half is measured, so it is. Below is what it scored, what one prompt change cost, and why that change was rejected.

Public demo mode. Real financial ingestion is disabled on this deployment by design. There is no database attached, the transaction endpoints are not registered, and no API key is present.

Every figure on this page is an aggregate. No transaction, amount, merchant, date, or per-row prediction is published here or reachable from here. The evaluations ran locally against real statements; only the counts travelled.

The dataset

Real bank and credit-card exports from three institutions, imported once and labelled by hand. Nothing synthetic, and nothing generated by a model.

Every row was annotated twice, independently, before the labels were reconciled — so the ceiling on any model score is a measured number rather than an assumption. Cohen's kappa is reported next to raw agreement because where one category dominates, 92% raw agreement can mean very little.

How the benchmark was built

Three decisions do most of the work here, and each of them makes the reported number smaller rather than larger.

The split is merchant-disjoint, not random

Rows are assigned by a salted hash of the normalised merchant, so every transaction from one merchant lands on the same side. A shuffled split would put four Kroger rows in development and a fifth in evaluation, and the score would be measuring memorisation of a merchant string. Merchants appearing on both sides: —.

It is a frozen validation benchmark, not a test set

The v1 results informed the design of v2. Once results shape a decision, the rows that produced them can no longer serve as a held-out test set, and calling them one would claim more than they can support. They are frozen, and they are honest about what they are.

Four metrics, because each is misleading alone

Macro F1 weights every category equally, so a model that ignores rare categories cannot hide behind the common ones. Weighted F1 says what a typical row experiences. Coverage and accuracy-when-answered separate declining to guess from guessing wrong. They are reported together on purpose — see the prompt experiment below for what happens when one of them is read on its own.

Failure analysis

What the selected prompt still gets wrong, stated plainly rather than averaged away.

  • Travel against transit. The largest single confusion. A rideshare to an airport and a rideshare to work look identical in a description line; the distinction lives in context the model is not given. This is the next prompt version, deliberately deferred until the v2 result was recorded.
  • LIVING_OTHER as a catch-all. Predicted 18 times against a true support of 1. v2 was written to fix exactly this and did not move it at all, which is the most useful thing the experiment produced.
  • Refunds read as transfers. A credit posting to a card is a refund or a payment depending on where the money came from, which the description does not say.
  • Five categories have fewer than five rows. The evaluation report says so in a warning block rather than in a footnote, because macro F1 weights those equally with the large classes and one correction moves the headline several points.

Architecture

The constraint that shapes everything: the model is a proposal, never a calculation.

  • The domain layer is standard-library only. No framework, no ORM, no HTTP client can be imported into it. An import-linter contract fails the build if one is, so the rule is enforced rather than documented.
  • Money is Decimal end to end, and crosses the HTTP boundary as a string. A contract test scans every response for a JSON float and fails on any of them.
  • The model sits behind a port. The prompt is a versioned artifact (categorise/v1), the provider is swappable, and the labels, split, and scoring stay fixed across providers so a second vendor can be scored on the identical benchmark.
  • Imports are fingerprinted and versioned. Every transaction carries a reproducible fingerprint and an occurrence number; snapshot and incremental modes have defined, and different, duplicate semantics, and an account cannot silently switch between them.
  • Tests run against real PostgreSQL in CI, not SQLite. Partial unique indexes and JSONB behave differently enough that a passing SQLite suite would be evidence of nothing.
