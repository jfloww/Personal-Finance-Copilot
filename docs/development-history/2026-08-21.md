# 2026-08-21 — a review, and what it found

**Commits:** `8ad5d1c` … `69c3bb5` (9)

## Where the day started

PR #1 had merged the evening before: transaction persistence, with a fingerprint
deciding what counts as a duplicate. A review of that commit was the first work
of the day, and it did not go well for the code.

## What the review found

The fingerprint is the load-bearing identity for the whole import path — it
decides what is a duplicate and what is new money. Three of its inputs were
unnormalised, and each broke deduplication on its own.

**The amount was hashed before quantisation.** `-4.50` and `-4.5` produced
different fingerprints, so the same charge stored twice. Worse, the row was
*persisted* quantised, so no stored fingerprint could be recomputed from its own
row — which forecloses ever rebuilding the index.

**The account was case-sensitive free text.** `--account=Checking` in August and
`--account=checking` in September built two complete parallel copies of one
statement, and reported both as clean imports with zero already-stored rows.
Verified against the repo's own environment: `count('Checking') == 1`,
`count('checking') == 1`.

**The fingerprint embedded an evolving heuristic with no version stamp.** It
hashed `normalise_description` output. Adding one prefix to `_PROCESSOR_PREFIX`
would silently re-import every stored transaction, undetectably.

Alongside those, the CLI had become a write path while keeping preview-era
argument handling: it rendered a preview and committed in the same invocation,
and silently discarded unrecognised flags — so `--dayfirst`, a missing hyphen,
vanished and every row committed with an eleven-month date error.

## What was decided

The corrective pass was specified rather than patched ad hoc, because the
central problem is not a set of bugs but an ambiguity nobody had written down:

> A fingerprint plus a per-file occurrence number cannot distinguish a genuine
> third identical charge from one already stored. The deciding fact is not in
> the file — it is a fact about how the file was produced.

The original code chose one reading silently. An unconditional offset by the
maximum stored occurrence chooses the other reading silently. So the design
declares the mode instead of inferring it, and refuses incremental mode outright
without a stable bank transaction id.

## What was got wrong today

**The plan's Task 1 was incomplete in a way that would have turned CI red for
eleven tasks.** Setting `CONNECTION_STRING` to a fresh container meant the
pre-existing integration tests finally *ran* — against a database with no
tables, because the plan never specified an `alembic upgrade` step. It could not
have surfaced from the steps written: Task 1's verification ran the suite only
locally, against an already-migrated database.

**Signed zero.** `Decimal("-0.001").quantize(2dp)` is `Decimal("-0.00")`, which
formats as `"-0.00"`, but PostgreSQL `NUMERIC` has no negative zero. Verified
both halves against the live database: a sub-cent negative would store a
fingerprint that could never be recomputed from its own row — the exact property
the module's docstring claimed. Found by review, not by the tests.

## Ruling

**Fix the signed-zero case now rather than defer.** Cost if wrong: three lines of
normalisation on an input range real statements may never produce. Cost of
deferring: a later reproducibility test either fails, or passes only because no
fixture happens to use a sub-cent negative — which is worse, because it would
certify a property that does not hold.
