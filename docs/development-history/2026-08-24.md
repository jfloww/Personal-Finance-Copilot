# 2026-08-24 — the first real evaluation, one change rejected, one adopted

**Verified today:** 1186 tests passing, all five checks green. 400 rows
labelled twice by hand, 135 scored against a live model four times, two prompt
changes measured — one rejected, one adopted. The showcase merged and deployed;
V2 is open as PR #3.

The day ran long enough to have two halves. The first is below; the second
starts at *Later the same day*.

## What shipped

- **A reproducible 400-row subset** (`0cb5d3c`) — merchants capped at five,
  singletons drawn across amount bands, Zelle counterparties masked to stable
  `PERSON_NNN` aliases derived by hashing, so no mapping file exists anywhere
  to leak.
- **Four taxonomy additions** (`a3b346e`, `b8f0701`, `2d0936a`, `fc73211`) —
  clothing, education, one merged insurance category, and the card annual fee,
  all found by annotating rather than by design.
- **Per-model pricing** (`52ac78e`) — a single pair of constants had priced
  every model at the dearest one's rate.
- **The first live evaluation**, then a second under a changed prompt, both
  archived under `docs/eval/runs/`.
- **The public evaluation artifact and landing page** — aggregate results only.

## The result

Claude Haiku 4.5 against the frozen 135-row benchmark, under `categorise/v1`:

```
                       macro F1  weighted  accuracy  coverage
rules                    0.0464    0.0549    0.0667    0.2000
llm:claude-haiku-4-5     0.4277    0.7201    0.6593    1.0000
hybrid                   0.4223    0.7142    0.6519    1.0000
```

$0.2404 for 135 rows, $0.00178 each, p50 1358ms and p95 1859ms.

The gap between the rule floor and the model is the number worth having. The
gap between macro F1 and weighted F1 is the honest part: 0.72 is what a typical
row experiences, 0.43 is what happens when the twenty-one categories are
weighted equally, and the difference is entirely the small classes.

## The change that was tried and rejected

`LIVING_OTHER` was predicted 18 times against a true support of 1 — a catch-all
absorbing rows that belonged elsewhere. v2 added five lines to the prompt making
it an explicit last resort, changed nothing else, and ran against the same rows,
same model, same split, same scoring.

| | v1 | v2 |
|---|---|---|
| macro F1 | 0.4277 | **0.4397** |
| weighted F1 | **0.7201** | 0.7108 |
| accuracy | **0.6593** | 0.6519 |
| cost | **$0.2404** | $0.2517 |
| p95 latency | **1859ms** | 3000ms |
| `LIVING_OTHER` F1 | 0.1053 | 0.1053 |

Macro F1 went up. Everything else went down, and the number the change was
written to move did not move at all.

**Why macro F1 rose is the finding.** The macro average divides by the union of
labels the benchmark contains and labels the system predicts. v2 stopped
predicting `LIVING_GYM` — never correct here — so its denominator fell from 21
to 20. The *summed* per-label F1 dropped, from 8.9814 to 8.7936. The mean rose
because the divisor shrank.

Four categories regressed (`INCOME`, `LIVING_GROCERY`, `REFUND`, `TRANSFER`)
against two improvements (`LIVING_SUBSCRIPTIONS`, `LIVING_TRAVEL`).

v2 is rejected and kept. Every scored version stays in `SYSTEM_PROMPTS`, and
`--prompt` selects one, so an archived score can still be reproduced from the
code that produced it. A change that was tried and measured is evidence;
deleting it would leave only the successes.

## Rulings

**Macro F1 is not a misleading metric. Deciding on macro F1 alone is.** It is
the metric that stops a model hiding a rare class it ignores, which is why it
is the headline. It is also the one most easily moved by something other than
getting better, as above. The report prints four numbers together for exactly
this reason, and today was the day that stopped being a precaution.

**135 rows is a frozen validation benchmark, not a test set.** The v1 results
informed the design of v2. Once a result has shaped a decision, the rows behind
it can no longer be described as held out, and calling them a final holdout
would claim more than they can support. Renamed everywhere, including on the
public page.

**Aggregate results ship; nothing row-level does.** `build_public_results.py`
reads the archived reports — not the database — and emits counts and rates.
It runs on a machine that has never seen the transactions. A contract test
scans the published payload for merchant names, dates outside the generation
timestamp, credentials, and any list long enough to be per-row.

**The published decision is pinned to the code.** A test asserts that
`prompt_experiment.selected_prompt` equals `PROMPT_VERSION`. Switching the
default prompt without re-running the evaluation now fails the build, rather
than leaving a public page claiming a decision the code no longer implements.

## What was got wrong today

**The token estimate was three times too low.** `ESTIMATED_INPUT_TOKENS = 450`
came from an offline smoke test; the measured figure is ~1,301 per call, because
the prompt carries the full taxonomy every time. The estimate exists to let
someone say no, and it was under-stating — the one direction it must never err
in. Now 1,400/110, measured and labelled as such.

Before that it had been five times too *high*, for the opposite reason: the
estimate priced every model at the dearest one's rate. Both errors were in the
same function, three commits apart.

**The evaluation report never recorded which prompt produced it.** The prompts
module opens by arguing that `"macro F1 0.81"` is not a result and
`"macro F1 0.81 under categorise/v1"` is one. The report printed the model and
the dataset checksum, and not the prompt version. The two archived runs are
distinguishable only by their filenames. Fixed going forward; the archived pair
is left as it is, and named in the artifact instead.

## The change that was tried and adopted

The development split, which v1 had never been measured against, showed two
categories failing outright:

- **`REFUND` scored F1 0.0000 on 19 rows.** Not close — zero. Reading the
  model's own stated reasons showed why: it identified the merchant correctly
  and never noticed the money had come back. One answer literally said *"appears
  to be a credit or refund"* and then labelled the row with the category of the
  purchase it reversed. It reasons about what a merchant is before it reasons
  about which way the money moved.
- **`TRANSFER` lost 13 of 26 rows to `LIVING_CARD_FEE`.** The model recognised
  card bill payments correctly — *"likely a credit card bill payment"* — and then
  picked the fee category, because nothing in the prompt distinguished paying a
  balance from being charged a membership fee.

v3 adds two rules to v1, not to the rejected v2. Both were checked against
development gold *before* being written: card payments are `TRANSFER` 7/7,
inbound person-to-person credits are `REFUND` 8/8, no counterexamples.

## The finding worth more than the result

| | Development (tuned on) | Benchmark (independent) |
|---|---|---|
| Macro F1 | 0.4263 → 0.5699 (**+0.1436**) | 0.4277 → 0.4724 (**+0.0447**) |
| Accuracy | 0.6302 → 0.7434 | 0.6593 → 0.6667 |
| `REFUND` F1 | 0.0000 → 0.6896 | 0.6667 → 0.6667 |
| `TRANSFER` F1 | 0.3111 → 0.7576 | 0.8421 → 0.8292 |

**The fix that transformed development barely moved the benchmark, and moved it
through a different category entirely.** `REFUND` was already at 0.6667 on the
benchmark under v1 — the failure the rule was written for did not exist there.
The benchmark's gain came mostly from `LIVING_CARD_FEE`, 0.0000 → 0.5000.

Merchant-disjoint splitting produces genuinely different difficulty on each
side. That has been asserted in this repository since the splitter was written;
today is the first time it was measured. The development number is what tuning
buys. The benchmark number is what generalises.

## Macro F1, a second time

v3's macro gain decomposes the same way v2's did, and the difference between
them is the whole argument:

|  | v2 | v3 |
|---|---|---|
| labels in the average | 21 → 20 | 21 → 20 |
| summed per-label F1 | 8.9814 → **8.7936** | 8.9814 → **9.4480** |
| macro F1 | 0.4277 → 0.4397 | 0.4277 → 0.4724 |

Both shrank their denominator by dropping a never-correct label. v2's summed F1
*fell* while its mean rose — the entire gain was arithmetic. v3's summed F1
rose, so roughly half its gain (+0.0222 of +0.0447) is better answers and half
(+0.0225) is the smaller divisor.

v3 was adopted on accuracy, weighted F1, and latency — none of which carry that
artifact — rather than on the macro number. Every macro move now ships with its
denominator and summed F1 beside it, so a reader never has to take the mean on
trust.

## Rulings

**Ambiguity stays authored, never inferred.** 31 of 400 rows have two annotators
who chose differently. Converting those into acceptable-label sets would have
filled the empty ambiguous stratum and raised every system's score. It was
refused, because the loader has said since it was written that *disagreement
usually means one annotator was wrong*. Those rows are reported instead as a
**difficulty** stratum, which measures whether the model struggles where people
did and claims nothing about the rows having two right answers.

Cost if wrong: the benchmark reports acceptable-label accuracy that equals exact
match, and says so, rather than a softer number that would have looked better.

**Prompt changes are chosen on the development split.** v2's failure was not
only that it did not work — it was chosen by looking at the benchmark. v3 was
designed from 265 development rows and measured on the benchmark exactly once,
afterwards. `--split development` exists to make that the easy path.

**Predictions are recorded and never published.** They make failure analysis and
re-scoring free. They are also a file of real transaction ids beside what a
model thought of each one, so they live under a git-denied path and the public
artifact is built from rendered reports instead.

**A rule baseline scored on the split it was fitted on is a lookup table.** On
development, `rules` scored macro F1 **1.0000**, and `rules_right_model_wrong`
came to 98 rows. Both are artifacts. On the benchmark the same bucket is 1 row
against 82 the other way. The development-split failure analysis is useful for
finding model failures and useless for comparing the two systems, and the
report now says so where it matters.

## What was got wrong today

**My line-ending check was silently broken, and every reading from it was
meaningless.** Before committing I ran `grep -c $'\r'` to compare committed and
working-tree files. The pattern was not surviving into `grep`, so it matched
*every* line and reported line counts. Several "no churn here" conclusions
during the day were that. Caught only when a two-line edit produced a
`+1201/-1200` diff and the numbers refused to make sense — `600 + 601` is not a
coincidence.

Replaced with `git cat-file blob` and a byte count in Python, which found the
one file that had genuinely flipped: `prompts.py`, LF in the repository and CRLF
after a `Path.write_text` round-trip on Windows. That is the actual mechanism —
`read_text` normalises CRLF to LF in memory and `write_text` translates back to
`os.linesep` — and it had been the cause all along.

The mechanism then claimed one more victim: this entry. Writing it with
`Path.write_text` flipped the file LF to CRLF and turned a 188-line addition
into a 306-line rewrite, inside the commit documenting the bug. The lesson is
not *be careful with `write_text`* - it is that on Windows the only safe way to
preserve a file's line endings is `read_bytes` / `write_bytes`.

**A real merchant name went into the public landing page** — a grocery chain
this dataset actually contains, used in a sentence explaining why the split is
merchant-disjoint. It is not repeated here, for the reason that made it a
mistake there. The *payload* had been
scanned for merchant names from the first draft; the prose around it had not.
Caught by scanning the diff before pushing. The containment test now runs
against every served page as well as the JSON, verified by reinserting the name
and watching it fail.

**A cost figure in the artifact was typed by hand and wrong.** The prose said
"9.6% more cost per row" beside a computed field reading 7.4%. Now bound to the
computed value with an f-string, so the two cannot disagree again.

**The four run logs were dated 2026-08-25 on 2026-08-24** (`be67906`). Every
other file in `docs/eval/runs/` is named for the local date it was produced. The
`generated_at` inside the artifact was already right — it is UTC, where the same
moment is the 25th — which is exactly what made the filenames look plausible.
