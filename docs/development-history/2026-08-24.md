# 2026-08-24 — the first real evaluation, and the first rejected change

**Verified today:** 1145 tests passing, all five checks green. 400 rows
labelled twice by hand, 135 scored against a live model twice, one prompt
change measured and rejected. Nothing deployed yet.

## What shipped

- **A reproducible 400-row subset** (`0cb5d3c`) — merchants capped at five,
  singletons drawn across amount bands, Zelle counterparties masked to stable
  `PERSON_NNN` aliases derived by hashing, so no mapping file exists anywhere
  to leak.
- **Four taxonomy additions** (`a3b346e`, `b8f0701`, `2d0936a`, `fc73211`) —
  clothing, education, one merged insurance category, and the card annual fee,
  all found by annotating rather than by design.
- **Per-model pricing** (`52ac78e`) — a single pair of constants had priced
  every model at the dearest one's rate.
- **The first live evaluation**, then a second under a changed prompt, both
  archived under `docs/eval/runs/`.
- **The public evaluation artifact and landing page** — aggregate results only.

## The result

Claude Haiku 4.5 against the frozen 135-row benchmark, under `categorise/v1`:

```
                       macro F1  weighted  accuracy  coverage
rules                    0.0464    0.0549    0.0667    0.2000
llm:claude-haiku-4-5     0.4277    0.7201    0.6593    1.0000
hybrid                   0.4223    0.7142    0.6519    1.0000
```

$0.2404 for 135 rows, $0.00178 each, p50 1358ms and p95 1859ms.

The gap between the rule floor and the model is the number worth having. The
gap between macro F1 and weighted F1 is the honest part: 0.72 is what a typical
row experiences, 0.43 is what happens when the twenty-one categories are
weighted equally, and the difference is entirely the small classes.

## The change that was tried and rejected

`LIVING_OTHER` was predicted 18 times against a true support of 1 — a catch-all
absorbing rows that belonged elsewhere. v2 added five lines to the prompt making
it an explicit last resort, changed nothing else, and ran against the same rows,
same model, same split, same scoring.

| | v1 | v2 |
|---|---|---|
| macro F1 | 0.4277 | **0.4397** |
| weighted F1 | **0.7201** | 0.7108 |
| accuracy | **0.6593** | 0.6519 |
| cost | **$0.2404** | $0.2517 |
| p95 latency | **1859ms** | 3000ms |
| `LIVING_OTHER` F1 | 0.1053 | 0.1053 |

Macro F1 went up. Everything else went down, and the number the change was
written to move did not move at all.

**Why macro F1 rose is the finding.** The macro average divides by the union of
labels the benchmark contains and labels the system predicts. v2 stopped
predicting `LIVING_GYM` — never correct here — so its denominator fell from 21
to 20. The *summed* per-label F1 dropped, from 8.9814 to 8.7936. The mean rose
because the divisor shrank.

Four categories regressed (`INCOME`, `LIVING_GROCERY`, `REFUND`, `TRANSFER`)
against two improvements (`LIVING_SUBSCRIPTIONS`, `LIVING_TRAVEL`).

v2 is rejected and kept. Every scored version stays in `SYSTEM_PROMPTS`, and
`--prompt` selects one, so an archived score can still be reproduced from the
code that produced it. A change that was tried and measured is evidence;
deleting it would leave only the successes.

## Rulings

**Macro F1 is not a misleading metric. Deciding on macro F1 alone is.** It is
the metric that stops a model hiding a rare class it ignores, which is why it
is the headline. It is also the one most easily moved by something other than
getting better, as above. The report prints four numbers together for exactly
this reason, and today was the day that stopped being a precaution.

**135 rows is a frozen validation benchmark, not a test set.** The v1 results
informed the design of v2. Once a result has shaped a decision, the rows behind
it can no longer be described as held out, and calling them a final holdout
would claim more than they can support. Renamed everywhere, including on the
public page.

**Aggregate results ship; nothing row-level does.** `build_public_results.py`
reads the archived reports — not the database — and emits counts and rates.
It runs on a machine that has never seen the transactions. A contract test
scans the published payload for merchant names, dates outside the generation
timestamp, credentials, and any list long enough to be per-row.

**The published decision is pinned to the code.** A test asserts that
`prompt_experiment.selected_prompt` equals `PROMPT_VERSION`. Switching the
default prompt without re-running the evaluation now fails the build, rather
than leaving a public page claiming a decision the code no longer implements.

## What was got wrong today

**The token estimate was three times too low.** `ESTIMATED_INPUT_TOKENS = 450`
came from an offline smoke test; the measured figure is ~1,301 per call, because
the prompt carries the full taxonomy every time. The estimate exists to let
someone say no, and it was under-stating — the one direction it must never err
in. Now 1,400/110, measured and labelled as such.

Before that it had been five times too *high*, for the opposite reason: the
estimate priced every model at the dearest one's rate. Both errors were in the
same function, three commits apart.

**The evaluation report never recorded which prompt produced it.** The prompts
module opens by arguing that `"macro F1 0.81"` is not a result and
`"macro F1 0.81 under categorise/v1"` is one. The report printed the model and
the dataset checksum, and not the prompt version. The two archived runs are
distinguishable only by their filenames. Fixed going forward; the archived pair
is left as it is, and named in the artifact instead.
