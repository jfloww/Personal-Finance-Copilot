## The Critical that twelve rounds of review missed

The per-task reviews ran twelve times and the whole-branch review found something
none of them could, because no single task owned both sides of it:

```
snapshot import  -> 1 written
incremental      -> 1 written, 0 already-stored
TOTAL ROWS for one real charge: 2
```

Snapshot rows carry `external_id = NULL`. The incremental dedupe check reads
only non-NULL ids, so snapshot rows are invisible to it — and the occurrence
offset then steps *past* those same rows, so the unique constraint does not fire
either. Import August as a snapshot, switch to incremental when the bank starts
supplying ids, and every overlapping charge duplicates silently.

Now refused: `import_csv` reads the account's prior batch modes and rejects a
mode change. `import_batches.mode` had recorded exactly the fact needed to
detect this since the schema landed, and nothing had read it back.

## Real exports, and three things they broke

The importer had been hardened for two days against fixtures written by the
person hardening it. The first real files found three defects in an afternoon.

**206 junk rows in a Chase checking export.** 188 rows where all seven fields
are empty, and 18 carrying a literal `"1"` in a column the mapping never reads —
interleaved, not trailing, so they could not be chopped off the end. Refusing the
whole file was correct and useless. New rule: *a row where every column the
mapping uses is empty is not a transaction.* Verified across all six files before
adopting it — it sets aside exactly those 206 and touches nothing else, and no
file anywhere holds a row partially empty in its mapped columns, so it never has
to guess.

**The preview named the wrong column.** Capital One carries both `Transaction
Date` and `Posted Date`; detection prefers the former, and `--map` correctly
overrode it — but `render()` printed the *detected* mapping, so the one screen
whose job is showing what will happen named one column while the import read
another.

**Amex writes charges positive.** Every other bank here writes money out as
negative. Read at face value, 245 Amex rows had every charge stored as income and
every payment as spending — the precise double-count `entities.py` warns about:
*"Both totals are then wrong, in opposite directions, and they look plausible."*

## What was got wrong today

**The sign convention was verified on one file and generalised to all of them.**
Capital One's split debit/credit columns were checked row by row — 317 debits
negative, 19 credits positive, zero sign errors — and reported as proven. Amex
was never checked. The importer negates a `Debit` column correctly; a signed
`Amount` column it takes at face value, and Amex's face value is backwards.

**The first fix for it did not work, and was nearly declared a success.**
`--sign` was added, verified on `preview`, and wired into the commit path —
except the edit silently did not match. The check used was `grep -c amount_sign`,
which counted a *comment*. 245 rows were deleted and re-imported still inverted.
Caught only by checking the sign distribution afterwards instead of trusting
`committed 128 of 128 rows`.

There is now a test that fails if `--sign` parses but never reaches the request.

**A `--yes` was left in a command whose own comment said to remove it.**

## Rulings

**`AmountSign` is declared, never detected.** A month of mostly refunds is real,
so the numbers cannot settle which convention a file uses. The preview *warns*
when a signed file is mostly positive — the check that would have caught this on
day one — but only the person who downloaded the file can decide.

**Snapshot windows come from the export's stated coverage, not observed dates.**
Two Capital One rows had a transaction date of 2025-12-31 and a posted date of
2026-01-02. Widening snapshot authority into December because a transaction date
crossed the boundary would claim coverage the export does not have; instead the
account maps `Posted Date`, and all 336 rows fall inside the declared window.

Cost if wrong: `posted_on` now means posting date on six of seven accounts and
something unstated on the two Amex ones, whose exports carry a single undocumented
date column. Recorded rather than smoothed over.
